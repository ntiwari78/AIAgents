## Context Engineering Foundations (14:24–14:34 - 10 min)

### Week-one transition and agent landscape

* Week one, day four concludes four theory days focused on using agentic frameworks to apply LLMs to commercial problems; the first project is a deployable digital twin scheduled for week one, day five
* Agent offerings fall into four categories: agent builders, products, runtimes such as [AWS Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html), and frameworks
* Frameworks range from lightweight OpenAI Agent SDK, Google ADK, and AWS Agents to more opinionated CrewAI and heavyweight LangGraph
* Frameworks are optional; equivalent behavior can be implemented with manually written JSON, LLM calls, `while` loops, and `if` statements

### Tools, loops, and context

* An AI agent is defined as an LLM call with tools in a loop to achieve a goal; the software decides how to interpret generated tokens and when to call tools
* **Context components**:

  * System prompts and instructions define the overall task
  * User prompts provide the current message
  * Available tools are described using JSON
  * Structured output constrains responses to a JSON schema that application code can convert into Python objects
  * Short-term memory is conversation history and current state
  * Long-term memory is relevant information retrieved from prior conversations, typically through tools or RAG
  * Agentic RAG increasingly retrieves information through tools rather than performing one-time retrieval before the prompt
  * Context categories overlap; no universal formula determines whether information belongs in a prompt, memory, RAG, or a tool
  * Context engineering requires a test set, an evaluation method, and experiments with instructions, tools, memory, RAG, and context organization

## Digital Twin Build and Refactoring (14:34–14:47 - 13 min)

### Pushover notification setup

* [Pushover](https://pushover.net/) provides phone push notifications for the deployed twin; the service is free for the first month and inexpensive afterward
* The Pushover user key starts with `U`; the application/API token starts with `A`
* `.env` variables must be stored as `PUSHOVER_USER` and `PUSHOVER_TOKEN`; the file must be saved before loading environment variables
* Pushover is optional; writing notifications to a file remains an alternative

### Twin tools and tool-call handling

* The twin receives two tools: `record_user_details` for contact interest and `record_unknown_question` for unanswered questions
* `record_user_details` accepts `email`, optional `name`, and optional `notes`; only `email` is required
* `record_unknown_question` is instructed to report every question the twin cannot answer; stronger wording or additional system-prompt instructions may be needed for smaller models
* Manual dispatch maps tool names to functions with `if` statements; Python `globals()` provides a more dynamic lookup but is unsafe because it exposes unrelated global functions
* A production implementation should use an explicit tool map to restrict the LLM to approved functions

### System prompt and notebook validation

* The system prompt uses LinkedIn profile and summary text, redirects unrelated questions to professional topics, and instructs the twin to record unanswered questions
* Prompt wording should be iterated for the specific profile, intent, and model rather than treated as universally correct
* The notebook version successfully records an unanswered question and a contact request using `test@testy.com`

### Python module structure

* `context.py` loads the LinkedIn profile and summary, then constructs the system prompt
* `tools.py` contains Pushover notification logic, the two tools, their JSON schemas, and the safer tool map
* `styles.py` defines UI styling and example questions; coding agents can help create a distinctive Gradio design
* `app.py` imports the other modules, calls OpenAI, launches the Gradio interface, and supplies example questions
* Notebook experimentation supports context engineering; once results are satisfactory, code can be productionized into modules and strengthened with unit tests
* `uv run app.py` runs the application with the configured Python environment

## Hugging Face Deployment (17:27–17:37 - 10 min)

### Authentication and deployment commands

* [Hugging Face Spaces](https://huggingface.co/docs/hub/en/spaces-overview) hosts the Gradio application; CPU basic is the free hardware option
* Login can be performed with `uvx huggingface-cli login --token`; `uvx huggingface-cli whoami` verifies the authenticated account
* Store the Hugging Face credential in `.env` as `HF_TOKEN`; the token begins with `hf`
* From the `twin` directory, deployment uses `uv run gradio deploy`
* The deployment prompts accept defaults for app title `Twin`, module `app.py`, and CPU basic hardware; secrets are added separately rather than through the deployment prompt

### Live twin and operational considerations

* The deployed Space becomes publicly accessible and can notify the owner when it receives an unanswered question or contact email
* Hugging Face provides a public repository containing the uploaded code, an embeddable Space, and settings for deleting the deployment
* Re-running `uv run gradio deploy` publishes updates; deleting the generated `README` file allows a fresh deployment questionnaire
* API costs should be controlled with cheaper models, fixed-budget API keys, OpenRouter limits, rate limiting, or by taking the Space offline when not needed

## Visible Checklist Agent Loop (17:38–17:46 - 8 min)

### Checklist tools and loop implementation

* A terminal UI makes the agent loop visible through a retro-style interface and a checklist that is updated as work progresses
* The two tools are `create_checklist`, which creates a checklist from descriptions, and `mark_complete`, which completes an item by one-based position with completion notes
* `handle_tool_calls` dispatches returned tool calls; the loop repeatedly calls the LLM while it requests tools, appends tool results, and stops when the model completes without tools
* The system prompt instructs the model to plan and execute a problem using checklist tools without asking for clarification

### Demonstration and takeaway

* The train puzzle used a train leaving Boston at 2 p.m. at 60 miles per hour and another leaving New York at 3 p.m. at 80 miles per hour toward Boston
* GPT-5.5 generated five checklist items, marked them complete while reasoning, and returned `4:06 PM`
* Checklist tools create a visible sense of planning and agency even though the implementation remains an LLM call, tool dispatch, and loop
* The exercise is to run the implementation with a different brain teaser and hand-code the agent loop from first principles
* Week one ends after initial agent calls, orchestration flows, tool calling, autonomy, the deployed digital twin, and the visible agent loop; week two focuses on the OpenAI Agents SDK
